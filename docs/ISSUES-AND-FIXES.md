# Chowly — Issues Found & Fixed During Testing

A running log of real problems hit while testing the deployed/local build, kept as they happened. Meant to be dropped into (or summarized in) the "How it behaves" section of the report — it shows the app was actually run and debugged, not just written once and assumed to work.

Each entry: what broke, why, what fixed it, where to find the fix.

---

### 1. Every failure showed as a generic "Unknown error"

**Symptom:** Any Supabase operation that failed (bad env vars, missing table, blocked query) returned the same unhelpful `"Unknown error"` message in the UI, no matter what actually went wrong.

**Root cause:** Every API route caught errors with `err instanceof Error ? err.message : 'Unknown error'`. Supabase-js doesn't throw real `Error` objects — it throws plain objects shaped like `{ message, details, hint, code }`. Since those objects aren't instances of `Error`, the check always failed and the real message was thrown away.

**Fix:** Added a shared `lib/errors.ts` helper (`getErrorMessage`) that also checks for a `.message` property on non-`Error` objects, and updated all 8 API routes to use it.

**Commit:** `fix: surface real Supabase error messages instead of generic 'Unknown error'`

---

### 2. Identifying as a customer failed: `new row violates row-level security policy for table "customers"`

**Symptom:** Entering a name on the Customer screen failed immediately, once error messages were actually visible (see #1).

**Root cause:** Supabase had Row Level Security enabled on the tables with no policies defined, which blocks all access — including from the app's own `anon` key — by default. This app has no login system, so there's no user/role for a row-level policy to check against in the first place.

**Fix:** Explicitly disabled RLS on every table in `supabase/schema.sql`, with a comment explaining why (access control is enforced in the service layer instead, since there's no auth system to base row policies on).

**Commit:** `fix: disable RLS on all tables, no login system exists to base policies on`

---

### 3. Ordering more than one item failed: `duplicate key value violates unique constraint "order_items_pkey"`

**Symptom:** Placing an order with a single item worked; adding a second item to the same order and submitting failed.

**Root cause:** Order-item IDs (`OIT001`, `OIT002`, …) are generated by asking the database "what's the highest ID currently in this table?" and adding one. The order-creation code generated an ID for each line item in a loop, but didn't insert any of them until *after* the whole loop finished — so for a 2-item order, both lines asked the "what's the highest ID?" question before either had been saved, got the same answer, and computed the same ID. The second insert then collided with the first.

**Fix:** Added `nextIds()` to reserve a whole block of sequential IDs from a single database lookup, and switched order-item creation to request all the IDs it needs up front instead of looping one at a time.

**Commit:** `fix: generate order-item ids as a batch, not one DB round-trip per item`

---

### 4. Switching to the Waiter view and back lost the customer's order

**Symptom:** After placing an order as a customer, flipping the role toggle to Waiter (to assign staff and serve it) and then flipping back to Customer landed on a fresh "what's your name?" screen — with no way to get back to the order to test payment or file a complaint, even though the order itself was untouched in the database and visible to the waiter the whole time.

**Root cause:** The Customer and Waiter views are two different React components, and the app only ever renders one at a time. Switching roles fully unmounts whichever view you're leaving, which destroys all of its in-memory state — including which customer you were and which order you'd just placed. This wasn't a database problem (the order was always safely stored); it was the browser losing track of *whose* order it was looking at.

**Fix:** Added a small `sessionStorage`-backed session (tab-scoped, no password, cleared when the tab closes — not a login) that the Customer view reads from the instant it mounts and keeps in sync as the order progresses. Flipping roles or refreshing the page now resumes the same customer and the same order automatically. Also added a "Not you?" link so a different customer on the same shared device can deliberately start over.

**Commit:** `fix: persist active customer session across role toggle and page refresh`

---

### 5. Hydration error on load: "the server rendered HTML didn't match the client"

**Symptom:** A red `Uncaught Error: Hydration failed...` in the browser console right after the customer session feature (#4) was added, with React showing the server had rendered the "enter your name" screen while the client immediately tried to render the "track your order" screen instead.

**Root cause:** The session-hydration code lived inside `useState`'s lazy initializer (`useState(() => loadCustomerSession().customer)`), which runs during render — not just on the client, but also as part of React's normal render pass. On the **server**, there's no `sessionStorage`, so it always rendered the empty/"enter your name" branch. On the **client's very first render** (the one React uses to compare against the server's HTML, before hydration is considered complete), `sessionStorage` *is* available, so if a session already existed, the client tried to paint a completely different tree than the server sent — the exact mismatch React was complaining about.

**Fix:** Moved the `sessionStorage` read out of the initializer and into a `useEffect`, which only ever runs in the browser *after* hydration has already reconciled against the server's HTML. The component now always starts in the same neutral "Loading…" state on both server and client, then swaps in the real session a moment later — a normal post-mount update, not a hydration mismatch.

**Commit:** `fix: hydrate customer session in an effect, not a useState initializer, to fix SSR mismatch`
